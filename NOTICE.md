## What was kept from opencode

The core packages relevant to a CLI + editor-extension coding agent: `opencode`, `core`, `cli`, `tui`, `protocol`, `schema`, `server`, `client`, `llm`, `plugin`, `session-ui`, `codemode`, `effect-drizzle-sqlite`, `effect-sqlite-node`, `httpapi-codegen`, `http-recorder`, `sdk`, `sdk-next`, `script`.

## Status

This is a work in progress, not yet a working product.

Landed: YukiOshi's permission modes (`manual`/`auto`/`auto-all`/`plan`) and hard safety blocks are now layered onto the inherited native `PermissionV2` service (`packages/core/src/permission.ts`, `packages/core/src/permission/guards.ts`, `packages/core/src/permission/risk.ts`). Hard safety blocks (protected paths, destructive shell commands) run unconditionally, before any configured ruleset or mode, and cannot be overridden even by `auto-all`. Modes only ever relax an "ask" toward "allow" — they never override an explicit `deny` rule. `plan` mode hard-blocks anything above low risk.

The mode is also reachable over the network API now: `GET/POST /api/session/:sessionID/permission/mode` (`packages/protocol/src/groups/permission.ts`, `packages/server/src/handlers/permission.ts`), regenerated into both `packages/client` (`getMode`/`setMode`) and `packages/sdk/js` (`client.v2.session.permission.mode.get/set`). The `yukioshi run`/`--mini` CLI has a new `--mode manual|auto|auto-all|plan` flag (`packages/opencode/src/cli/cmd/run.ts`) that sets it once at session start; `--auto`/`--yolo`/`--dangerously-skip-permissions` now also set server-side `auto-all` (previously they only drove a client-side auto-reply loop against the legacy V1 permission events, which is left in place as a fallback).

**Important correction to the above**: `PermissionV2` is *not* what actually gates tool execution in this codebase today. Tracing the real call path (`packages/opencode/src/session/tools.ts` → `packages/opencode/src/tool/registry.ts` → `packages/opencode/src/tool/{shell,edit,write,webfetch,...}.ts` → `packages/opencode/src/permission/index.ts`, the legacy V1 `Permission` service) shows the inherited codebase was mid-migration: `PermissionV2`/`packages/core/src/tool/*` exist and are wired into the dependency graph, but nothing in the live session/agent loop actually selects them yet. So the hard safety blocks and modes added to `PermissionV2` alone would have been inert for real usage. To close that gap:

- The same `SafetyGuards`/`RiskClassifier` modules are now also wired into the **live** V1 service (`packages/opencode/src/permission/index.ts`): hard blocks run unconditionally before rule evaluation, and `manual`/`auto`/`auto-all`/`plan` modes (`Permission.Service#getMode`/`#setMode`, in-memory per session) resolve `ask` the same way `PermissionV2` does. 88 tests (79 pre-existing + 9 new) pass.
- `yukioshi run`/`--mini`'s client-side permission loop (`packages/opencode/src/cli/cmd/run.ts`) is now risk-aware: `--mode auto` auto-approves only low-risk asks, `--mode auto-all`/`--auto`/`--yolo` approve everything not hard-blocked, `--mode plan` and default `manual` behavior are unchanged (both already reject/ask, matching prior behavior).
- The TUI (`packages/tui`, SolidJS/opentui)'s existing client-side permission toggle (`context/permission.tsx`, previously a 2-state `auto`/`normal`) is now the same 4 modes, cycled via the `permission.mode` command-palette entry, shown in the prompt status line, and resolved risk-aware in `context/sync.tsx`'s `permission.asked` handler. 5 new SolidJS integration tests cover all four modes (`packages/tui/test/cli/cmd/tui/sync.test.tsx`).
- This TUI/CLI-side mode selection is a client-side convenience layer only (mirrors how `--auto`/`--yolo` already worked before this change) - the hard guards are what actually can't be bypassed, since they run server-side in `Permission.Service#ask` regardless of what any client does.

Not yet done: a real server-side mode API for V1 (no HTTP route - V1's legacy routes use a different, Hono-based router than the effect `HttpApiGroup` system `PermissionV2` uses, and building that out was deferred; V1 mode is client-side-only for now, same as the pre-existing `--auto`/toggle it replaces). Also not done: `yukioshi run --mini`'s separate interactive footer runtime (`packages/opencode/src/cli/cmd/run/runtime.ts`) isn't mode-aware yet - only plain `run` and the full TUI are. And the legacy ACP bridge (`packages/acp/permission.ts`) isn't touched.

## Skills

opencode already had a Claude-compatible skills system of its own (`packages/opencode/src/skill/index.ts`, `packages/opencode/src/tool/skill.ts`) - SKILL.md discovery (YAML frontmatter + body), progressive disclosure (the model sees name/description in the system prompt, full instructions load on demand via the `skill` tool), and it already reads `~/.claude/skills`, `~/.agents/skills`, and project skill directories. It was missing the actual bundled skill *content* YukiOshi Code ships (`skills/` on `main`, Apache-2.0, from `anthropics/knowledge-work-plugins` plus a few written for YukiOshi): `packages/opencode/skills/` now has the same 26 skills (`bugfix`, `disaster`, `nightmare`, `skill-creator`, `web-artifacts-builder`, `design:*` x7, `engineering:*` x10, `productivity:*` x4 - namespaced by rewriting the `name:` frontmatter field, since opencode's discovery doesn't compute folder-based namespaces the way `packages/skills` on `main` does), scanned unconditionally alongside the existing `customize-opencode` built-in. `Skill.isBuiltin()`/`Skill.BUILTIN_SKILLS_DIR` were added so existing fixture-only tests can keep excluding built-ins by predicate instead of a single sentinel string; 12 pre-existing tests needed that one-line update. New test coverage: end-to-end loading of a real bundled skill (`skill-creator`, which has nested scripts/agents/references/assets) through the actual `skill` tool.

Not done: `packages/opencode/skills` is resolved relative to the source file at runtime (`fileURLToPath(new URL("../../skills", import.meta.url))`), which works for `bun run src/index.ts` but needs the directory copied alongside any future packaged/dist build - same caveat as `main`'s own README already states for its build step. Also not done: opencode's skill trust model doesn't yet distinguish untrusted repository-sourced skills from trusted user/builtin ones the way `packages/skills/src/SkillTypes.ts` on `main` does (`SkillSource`, `trusted`, symlink-escape protection via `within`) - a project's own `.yukioshi/skill/` (or legacy `.opencode/skill/`) or `.claude/skills/` skill is currently treated the same as a user's global one.

## Kilo Code features

This branch is also pulling in a small, deliberately-scoped set of features from [Kilo Code](https://github.com/Kilo-Org/kilocode) (itself MIT-licensed, a downstream fork of opencode) - not a full merge, since Kilo Code's own fork has grown to 300+ files covering entire product surfaces (cloud session sync, a plugin marketplace, telemetry, task boards, notebook support, etc.) well beyond YukiOshi's CLI+VS Code scope.

**OS-level sandbox** (landed): `packages/sandbox` (`@yukioshi/sandbox`) is Kilo Code's `@kilocode/sandbox` package ported essentially verbatim - bubblewrap confinement on Linux, `sandbox-exec` (seatbelt) on macOS, plus a network proxy with TLS-SNI-based host allowlisting for the "proxy" network mode. Kilo-specific identifiers were renamed (`@kilocode/sandbox` → `@yukioshi/sandbox`, `KILO_*` build constants → `YUKIOSHI_SANDBOX_*`, the `kilo:` proxy-auth username → `opencode:`); the actual sandboxing logic is untouched. 47 of the package's own tests pass in this environment (15 skip, correctly platform-gated to macOS/Windows).

Wiring into the live bash tool (`packages/opencode/src/tool/shell.ts`) is intentionally much simpler than Kilo's own: a new `sandbox` config block (`packages/core/src/v1/config/sandbox.ts` - `enabled`, `network: "allow"|"deny"`, `writablePaths`) resolved once per command, no live in-session toggling, no subagent-family inheritance, no persisted per-session preference store (all things Kilo's own `kilocode/sandbox/policy.ts` builds for its product UX but aren't needed for the core safety property). Off by default. Verified end to end in this environment: with `sandbox.enabled: true`, a command writing inside the workspace succeeds and a command writing to `/tmp` outside the workspace genuinely fails (bubblewrap `--ro-bind`), not just against a mock - see the two new tests in `packages/opencode/test/tool/shell.test.ts`. Building the profile also had to replicate a real edge case from `packages/opencode/src/project/instance-context.ts`: non-git projects set `worktree` to `"/"`, which would otherwise make the entire filesystem "writable" (the sandbox package's own `validate()` correctly caught this during testing - a real bug, not a false positive).

Wiring into in-process filesystem modification tools (`write.ts` and `edit.ts`): Kilo only guarded bash commands through bubblewrap/seatbelt, leaving direct `write` and `edit` tool calls unenforced by the sandbox boundary. The shared sandbox profile builder and path assertion helper (`packages/opencode/src/tool/sandbox-profile.ts` — `sandboxProfile()` and `assertSandboxWrite()`) now centralize this policy across `shell.ts`, `write.ts`, and `edit.ts`. In `write.ts` and `edit.ts`, `assertSandboxWrite` validates the target path against the sandbox profile's `allowWrite` / `denyWrite` / `denyNames` (`.git`) via `Sandbox.assertWrite()` before writing or editing. When `sandbox.enabled` is false, this is a zero-overhead no-op. When enabled, attempts to write outside the workspace/worktree (or into `.git`) fail immediately with a descriptive permission error before any disk mutation, while extra paths configured in `sandbox.writablePaths` are cleanly permitted. Tested with 8 new unit tests across `packages/opencode/test/tool/write.test.ts` (4 tests) and `packages/opencode/test/tool/edit.test.ts` (4 tests), all passing.

**Memory system** (landed): `packages/opencode/src/memory/` is a from-scratch, much smaller reimplementation of Kilo's `packages/kilo-memory` (6,700 lines) - that package's size comes almost entirely from automatic, LLM-driven capture (parsing every conversation turn to extract memories, a consolidation model call wired into Kilo's own session/turn lifecycle, token-budgeted ranking, session digests). None of that is ported. What's kept is the explicit surface and on-disk design: three markdown files per project (`project.md`/`environment.md`/`corrections.md`, stored under YukiOshi's own data dir keyed by a hash of the git root, the same git-root-detection and `## Section` / `- key :: text` format as Kilo, both ported close to verbatim since they're small and self-contained), exposed through two new tools (`memory_recall`, `memory_save`) the model can call explicitly - remember/correct/forget a fact, or search/list what's stored. Search is a simple substring/term-count ranking, not Kilo's token-budgeted retrieval engine. Gated behind a new `memory.enabled` config flag (off by default) - the tools aren't even registered when it's off, rather than registered-but-disabled. `memory_recall` is classified low-risk and `memory_save` high-risk in the shared `RiskClassifier` (so "auto" permission mode can read memory without asking but still asks before writing it). 19 new tests (14 on the storage layer directly, 5 end-to-end through the real tool registry and execute path - gating, remember→search→catalog→forget→search-again, and the corrections-file split), all passing, plus the full 1732-test regression sweep across `core` and `opencode` still green.

Not auto-injected into the system prompt yet (the model has to call `memory_recall` itself; Kilo auto-injects a catalog at session start) - deferred along with the auto-capture pipeline.

**Parallel/worktree-isolated subagent orchestration** (landed): Kilo's "Agent Manager" (`packages/opencode/src/kilocode/tool/agent-manager.ts` + `kilocode/agent-manager/*`, ~2,000 lines) turned out to be less of a gap than expected - the inherited codebase already ships a solid single-subagent `task` tool (foreground/background/resume) *and* a full native git worktree service (`packages/opencode/src/worktree/`, create/list/remove/reset). Kilo's own value-add over that is specifically running several subagents **concurrently**, optionally each in its own isolated worktree, plus a management board/host-process/batch-versions-comparison UI this port does not replicate.

What's landed is a new `task_parallel` tool (`packages/opencode/src/tool/task-parallel.ts`) that composes the two already-solid pieces rather than porting Kilo's board/host/protocol subsystem: it calls the existing, unmodified `task` tool's own `execute` concurrently (up to 4 at a time) for 1-8 requested tasks, and for any task with `worktree: true`, creates a real isolated git worktree via `Worktree.Service.create()` first and runs that task's subagent inside it via `InstanceStore.provide({directory: ...}, ...)`. Zero changes to `task.ts` itself - this is pure composition over its existing public interface. Gated behind a new `experimentalParallelTasks` flag (`YUKIOSHI_EXPERIMENTAL_PARALLEL_TASKS`), matching the project's own existing convention for new experimental tools (`experimentalLspTool`, `experimentalPlanMode`, etc.) rather than the config-flag pattern used for sandbox/memory.

Finding this tool's own real bug along the way: every `Tool.execute` in this codebase dies (via `Effect.orDie` in `tool.ts`'s wrapper) rather than failing with a typed error, so a per-task failure is a defect, not a catchable `Effect` error - `Effect.result` (which only inspects the typed error channel) silently let one failing task crash the entire batch in the first pass; fixed by catching with `Effect.exit`/`Cause.squash` instead, which is what actually intercepts a defect. Also had to fix a test-infrastructure ripple: adding `Worktree.node`/`InstanceStore.node` to the tool registry's dependency graph surfaced a previously-latent "unbound `InstanceBootstrap` node" error in every existing test file that compiles `ToolRegistry.node` without a bootstrap stub (`registry.test.ts`, `task.test.ts`, not just this port's own new test) - fixed by extracting the existing stub pattern into a shared, exported `noopBootstrapReplacement` in `test/fixture/fixture.ts`.

7 new tests (3 on `task_parallel` itself, including one that creates a real git worktree and verifies isolation, and one proving a failing task doesn't sink the batch; 2 registry-gating tests; the rest incidental to the fixture fix), full regression sweep across `core` and `opencode` passing.

Running the full `opencode` suite repeatedly while verifying this (and earlier commits) accumulated thousands of leftover test-run scratch directories under `/tmp` (tmpfs, 7.8G) until it hit quota (`EDQUOT`), which cascaded into ~200 unrelated test failures on one run - a self-inflicted environment issue from repeated full-suite runs in this session, not a code regression; confirmed by re-running the same tests clean after freeing `/tmp`. Two *real*, pre-existing issues surfaced during that investigation and are fixed here, both leftover from the earlier permission-mode commit rather than this one: `packages/opencode/test/event-manifest.test.ts` had its own hardcoded public-event count (missed when `packages/schema`'s copy of the same assertion was fixed at the time `PermissionV2.Event.ModeChanged` was added), and `packages/opencode/test/cli/help/__snapshots__/help-snapshots.test.ts.snap` had a stale `yukioshi run --help` snapshot from the `--mode` flag added in that same commit.

Also not done: macOS seatbelt is untested (ported but this environment is Linux-only).

**Semantic code search/indexing**: unlike the other Kilo features, this one didn't compose with anything opencode already had - it's genuinely new infrastructure. `packages/indexing` (`@yukioshi/indexing`) is Kilo's `@kilocode/kilo-indexing` ported close to verbatim: 8 embedding providers (OpenAI, OpenRouter, OpenAI-compatible, Gemini, Mistral, Bedrock, Vercel AI Gateway, Voyage), 2 vector store backends (LanceDB embedded, Qdrant server), tree-sitter-based symbol-aware chunking for ~25 languages (via the `tree-sitter-wasms` prebuilt grammar bundle), a file watcher, scanner, and cache layer, and a `CodeIndexManager` facade (`initialize`/`startIndexing`/`searchIndex`/`getCurrentStatus`). The one embedder actually dropped (not just renamed) is Kilo's own hosted "managed-indexing" service (`embedders/kilo.ts`) - it's Kilo-proprietary SaaS infrastructure that cannot work outside Kilo's own backend, and every place it touched (`AvailableEmbedders`/`EmbedderProvider` unions, `config.ts`'s `kilo` options block, `service-factory.ts`'s `kilo` branch, `model-registry.ts`'s Kilo catalog hook) was removed to match, not just stubbed. `.kilocodeignore` is still honored for migration alongside `.yukioshiignore` (and `.opencodeignore`). 498 of the package's own tests pass (9 skip, needing live credentials/platform-specific bindings the mocked suite doesn't cover); typecheck is clean.

The agent-side integration is wired in on top of that package: an `indexing` config block (`packages/core/src/v1/config/indexing.ts`, a deliberately thin passthrough record - real validation happens via `@yukioshi/indexing`'s own, much larger, already-tested zod schema at point of use, so the two don't drift), an `Indexing.Service` (`packages/opencode/src/indexing/index.ts`) that keys one `CodeIndexManager` per project (via `Project.Info.id`, not re-derived git-root hashing) and lazily initializes/starts it, and a `code_search` tool (`packages/opencode/src/tool/code-search.ts`), gated behind `indexing.enabled` the same way `memory_recall`/`memory_save` are gated behind `memory.enabled`. Classified `low` risk in `RiskClassifier` (read-only). While building this, tracing the enabled-but-unconfigured path (e.g. `indexing.enabled: true` with no provider API key) in Kilo's own `manager.ts` surfaced two real crash bugs in the integration layer, both fixed before landing: `ensure()` was calling `manager.startIndexing()` whenever the status was `"Standby"` and the feature was enabled, without checking `isFeatureConfigured` - but when unconfigured, the manager's internal services are never constructed, so `startIndexing()`'s (and `searchIndex()`'s) `assertInitialized()` throws. `code-search.ts` additionally called `indexing.search(...)` unconditionally whenever status wasn't `"Error"`, including `"Standby"`, hitting the same throw. Both are now short-circuited to a plain "not available yet" message instead of crashing, with a test (`test/tool/code-search.test.ts`) that exercises exactly this path - `indexing.enabled: true`, no credentials - and asserts a graceful result rather than an exception. No test in this suite needs live credentials or makes a network call.

**Claude-Code-compatible hooks** (landed, all six events): `main` already has a full, shipped implementation of this (shell-command hooks run at fixed points, JSON on stdin, exit code 2 or `{"decision":"block"}` blocks, stdout becomes context) - see `main`'s README "Hooks and web access" section and `packages/runtime/src/hooks/{HookRunner,HookBindings}.ts` on that branch, which this port's core logic (`packages/opencode/src/hooks/index.ts`) follows closely, adapted to Effect-TS and this fork's own process-spawning primitive (`CrossSpawnSpawner`/`effect/unstable/process`) instead of `main`'s `ProcessRunner`/`ShellDetector` abstractions. A new `hooks` config block (`packages/core/src/v1/config/hooks.ts`: `preToolUse`/`postToolUse`/`userPromptSubmit`/`sessionStart`/`stop`/`notification`, each an array of `{matcher?, command, timeoutMs?}`) feeds a `Hooks.Service` that spawns matching commands and parses the exit-code/JSON-decision/stdout-as-context semantics. Matchers match against native tool ids (`bash`, `edit`, `write`, ...), not Kilo's distinct tool-name space.

- **PreToolUse/PostToolUse** (`session/tools.ts`'s per-tool-call plumbing): PreToolUse runs (and can block, with the reason sent to the model) right before `item.execute`; PostToolUse runs right after and appends any blocked-feedback to the tool's output.
- **UserPromptSubmit** (`session/prompt.ts`'s `prompt()`): runs before the user's message is persisted/sent. A block throws a `NamedError.Unknown` with the hook's reason (same `throw`-inside-`Effect.gen`-becomes-a-defect convention already used in this file for "Agent not found") - the message is never created, the model is never called. Returned `context` is appended as extra synthetic text parts on the user message, same mechanism MCP resource descriptions already use.
- **SessionStart** (`session/prompt.ts`'s `prompt()`): fires once, on a session's first message only (checked via `sessions.messages({limit: 1})`), not on `Session.create()` directly - several `Session.create()` call sites are internal (subagents, tasks), not a user starting a top-level conversation, so hooking the message flow instead avoids over-firing. Its `context` feeds into the same injection as UserPromptSubmit's.
- **Stop** (`session/prompt.ts`'s `runLoop()`, right before the turn's final message is returned): fire-and-report only for now - `main`'s "agent continues with the reason as a new instruction (at most 3 times)" semantics for a *blocked* Stop hook are not implemented, documented as a gap rather than risking a subtle infinite-loop bug in this already-large function. Warnings are logged; `blocked`/`context` are currently ignored.
- **Notification** (`permission/index.ts`'s `ask()`, right where a request actually becomes pending and `Event.Asked` is published - not for auto-allowed/denied requests that never surface to the user): runs inline (not forked - `ask()`'s own `Effect.Effect<void, PermissionV1.Error>` signature has no `Scope` to fork into), bounded by the hook's own `timeoutMs`. Never decides anything, matching `main`'s semantics.

Two real, pre-existing bugs were found and fixed while building this, neither caused by the hooks feature itself: (1) `packages/core/src/cross-spawn-spawner.ts` - a child process that exits without ever reading stdin closes its end of the pipe, and writing to it afterward raises an EPIPE with zero listeners attached, which Node treats as an uncaught exception that crashes the *entire process*, not just the one Effect computation. Fixed with one defensive early `proc.stdin?.on("error", () => {})` listener, right where the process is spawned. Covered by a new regression test in `packages/core/test/effect/cross-spawn-spawner.test.ts` (verified it actually reproduces without the fix before confirming the fix). (2) A `LayerNode`-wiring gap: `Hooks.Service` is consumed fresh on every call inside `session/tools.ts` (a standalone, separately-invoked exported function), which requires *both* `Hooks.node` being a dependency of the specific node whose own construction needs it (`SessionPrompt.node`, not a mere sibling in some unrelated node's deps - that doesn't re-expose it) *and* an explicit `Effect.provideService(Hooks.Service, hooks)`/`Effect.provideService(Config.Service, config)` at `SessionTools.resolve(...)`'s call site, matching the existing `Effect.provideService` chain there for the other services `resolve()` yields fresh each call. Missing either half type-checks fine but fails at runtime with "Service not found: @yukioshi/Hooks" - caught by running the real HTTP/ACP integration test suite (`test/server/httpapi-sdk.test.ts`, `test/server/httpapi-session.test.ts`, `test/cli/acp/prompt-content.test.ts`), which a narrower unit-test-only verification pass would have missed entirely. By contrast, `permission/index.ts`'s `ask()` and `prompt.ts`'s `prompt()`/`runLoop()` are closures *inside* their service's own top-level construction effect, so pulling `hooks`/`config` once there and letting the closures capture them needed no extra wiring - the same pattern already used for `Plugin.Service`/`Permission.Service`/etc. in those files. `Hooks.node` is also listed as a top-level sibling in both `app-runtime.ts`'s and `server.ts`'s separately-maintained app graphs (see `knowledge.md`'s note on this exact gotcha), matching how `Config.node`/`Permission.node`/etc. are already globally available.

New tests: `packages/opencode/test/hooks/runner.test.ts` (8 tests, all spawning real shell commands - matcher filtering, exit-code-2 blocking, JSON-decision blocking/context, non-blocking warnings, multi-hook ordering, `has()`), a Notification test in `test/permission/next.test.ts` (verifies the real JSON payload delivered over stdin when a request actually surfaces), and two tests in `test/session/prompt.test.ts` (UserPromptSubmit blocking prevents any LLM call; SessionStart fires exactly once across two turns in the same session). Also fixed an unrelated, pre-existing `noopBootstrapReplacement` gap in `test/tool/skill.test.ts` and `test/session/prompt.test.ts` (same class of bug fixed earlier for `registry.test.ts`/`task.test.ts`, just missed then) discovered while running the full suite after this change - the latter had been silently failing to run at all (a compile-time crash before any test body executed), which is also how a genuine, unrelated, pre-existing timeout bug in `test/session/prompt.test.ts`'s "loop includes MCP instructions in model system context" test was discovered: it reproduces identically with none of this session's hook changes applied, confirmed via an isolated git worktree at the prior commit - flagged here for whoever owns the MCP system, not fixed, since it's outside this feature's scope.

Known gaps: a blocked Stop hook is currently reported but does not continue the agent with its reason, and secret redaction of hook payloads (`main`'s `HookRunner` has an optional `redact` callback) was not ported.

## Multi-provider model gateway

**Multi-provider presets** (landed): `packages/opencode/src/provider/provider.ts` keeps opencode's models.dev-backed, simultaneous-provider architecture and adds the missing YukiOshi-compatible profiles from `main`'s provider contract. `omniroute` is a model-configured OpenAI-compatible preset with `YUKIOSHI_API_KEY` then `OMNIROUTE_API_KEY` fallback; `google-ai-studio` aliases the catalog's Gemini metadata onto `https://generativelanguage.googleapis.com/v1beta/openai/` with `GOOGLE_API_KEY`, `GEMINI_API_KEY`, then `YUKIOSHI_API_KEY`; and `opencode-zen` aliases the OpenCode catalog onto `https://opencode.ai/zen/v1` with `OPENCODE_API_KEY` then `YUKIOSHI_API_KEY`. Configured `baseURL` and `apiKey` options still take precedence. The existing native Google, OpenRouter, and NVIDIA loaders remain in place; no bespoke HTTP client or single-provider gateway was copied from `main`.

Existing OpenRouter, NVIDIA, Vercel, ZenMux, LLM Gateway, and Kilo attribution headers were changed from opencode branding to `HTTP-Referer: https://github.com/ahmed-alxawad/YukiOshiCode` and/or `X-Title: YukiOshi Code` as appropriate. NVIDIA's billing-origin header now identifies YukiOshi Code. Coverage includes provider preset fallback/base-URL tests and the updated core provider-plugin header tests.

     - Schema sanitization: Moonshot expands `$ref` before validation and rejects sibling keywords like `description` on the same node; `transform.ts` strips them for `moonshotai` and any `kimi` model.
     - Adaptive reasoning effort mapping for thinking models without token budgets.
   - `packages/opencode/src/session/system.ts` already selects the dedicated `packages/opencode/src/session/prompt/kimi.txt` system prompt when any model ID containing `kimi` or provider `moonshotai`/`moonshotai-cn`/`kimi-for-coding` is active.
   - UI assets (`packages/ui/src/assets/icons/provider/kimi-for-coding.svg` and icon sprites) are already in place.
   - Conclusion: Kimi/Moonshot works out of the box with zero code changes.

2. **Repository investigation (`MoonshotAI/kimi-code`, MIT)**:
   - Evaluated Kimi Code's architecture (`packages/agent-core-v2`, `packages/kosong`, `packages/kaos`, `packages/minidb`, `packages/tree-sitter-bash`):
     - **Long-context handling**: In Kimi Code, long context is predominantly a model attribute (Moonshot's 256k-2M context windows with prefix cache discounts) rather than client-side algorithmic compression.
     - **Compaction (`fullCompaction`)**: Triggers at 85% context usage; prompts LLM for handoff summary (`compaction-instruction.md`); retains head user messages (up to 2k tokens) and tail user messages (up to 18k tokens, 20k total) while eliding middle user turns and dropping intermediate assistant/tool turns. Opencode already has an equivalent Effect-TS native compaction engine (`packages/opencode/src/session/compaction.ts` and `packages/core/src/session/compaction.ts`) with structured Markdown handoff templates, tail turn retention, and prior-summary merging.
     - **Tool result truncation (`toolResultTruncation`)**: Kimi Code caps inline tool output at 50KB / 2000 lines, writing the full output to disk (`tool-results/`) and returning a preview with a file pointer. Opencode already has the exact same mechanism in `packages/opencode/src/tool/truncate.ts` (capping at 50KB / 2000 lines in `TRUNCATION_DIR`, returning a preview and pointer for `Read`/`Grep`/subagent delegation).
     - **`packages/tree-sitter-bash`**: A ~20k-line pure-TypeScript bash AST parser used in Kimi Code for command analysis (`dangerous-command-ask.ts`). While interesting, this fork already has kernel-level enforcement via Linux bubblewrap (`packages/sandbox`) alongside `SafetyGuards` in `packages/core/src/permission/guards.ts`. An AST parser is an alternative defense layer, but bubblewrap provides strict OS-level containment.
     - **`packages/minidb`**: An embedded JSON document store with WAL. Opencode already uses SQLite via Effect/Drizzle and LanceDB/Qdrant for vector indexing (`packages/indexing`).
   - Conclusion: Nothing was ported. Forcing a port of Kimi Code's XState/DI-scoped engine components would create severe architectural impedance against Bun + Effect-TS without providing any capability opencode doesn't already possess.

## Evidence-based completion

**Ported from `main` (2026-10-02) — verified missing in opencode; scoped, built, and tested.**

1. **Investigation of `main` & `opencode-foundation` gap**:
   - In `main`, every agent task concludes with an evidence-backed verification summary (`VERIFIED`, `PARTIALLY_VERIFIED`, `FAILED`, `UNAVAILABLE`, `SKIPPED_BY_USER`) derived strictly from executed checks (syntax, diagnostics, typecheck, lint, tests) rather than model self-assessment.
   - An audit of `opencode-foundation` confirmed no equivalent concept existed under any naming: opencode only tracks LLM stream stop reasons (`stop`, `error`, `content-filter`), session UI activity states (`idle`, `busy`), and post-hoc git diffs (`SessionSummary`), with zero automated post-task verification planning or evidence aggregation.
2. **What was ported**:
   - **Schema contracts** (`packages/schema/src/verification.ts`, exported from `packages/schema/src/index.ts`):
     - `Verification.Status`: canonical union (`VERIFIED`, `PARTIALLY_VERIFIED`, `FAILED`, `UNAVAILABLE`, `SKIPPED_BY_USER`).
     - `Verification.CheckKind` (`syntax`, `diagnostics`, `typecheck`, `lint`, `test`, `build`, `diff`) and `Verification.CheckStatus` (`passed`, `failed`, `error`, `skipped`, `unavailable`).
     - `Verification.Check`: schema with kind, label, status, command, exitCode, durationMs, and bounded evidence excerpt.
     - `Verification.Summary`: schema with status, check array, and one-sentence derivation explanation.
   - **Pure status derivation** (`packages/core/src/verification/result.ts`):
     - `summarizeVerification()`: derives `FAILED` on any failure/error; `SKIPPED_BY_USER` when declined or all checks skipped; `UNAVAILABLE` when no checks configured; `VERIFIED` only when behavioral checks (`test`) pass with no failures or skips; and `PARTIALLY_VERIFIED` when only static checks pass or some checks were skipped.
     - `noChangesVerification()`: returns `UNAVAILABLE` with an explanation that no files were changed.
   - **Verification planning** (`packages/core/src/verification/plan.ts`):
     - `planVerification()`: builds the smallest meaningful sequence: syntax (JSON/JSONC files touched, excluding configs) → diagnostics (editor error diagnostics on touched files) → project commands in canonical order (`typecheck` → `lint` → `test`).
   - **Execution engine** (`packages/core/src/verification/engine.ts`):
     - `VerificationEngine`: executes in-process syntax checks (with UTF-8 BOM handling), collects error-level editor diagnostics, executes tool runners with 3,000-character evidence bounding, aborts early on typecheck failures (preventing doomed test runs), supports cancellation signals, and provides both Promise and native Effect (`verifyEffect`) entrypoints.
   - **Completion policy** (`packages/core/src/verification/policy.ts`):
     - `decideCompletion()`: evaluates whether verification should run or skip based on mode, change counts, and user preference.
   - **CLI wiring into `yukioshi run` (`packages/opencode/src/cli/cmd/run.ts` & `src/cli/cmd/run/verification.ts`)**:
     - Wires execution immediately following prompt completion (`client.session.prompt` and `args.command` post-turn resolution) without touching `session/prompt.ts` or `session/tools.ts`.
     - **Turn changed files detection (`detectTurnChangedFiles`)**: queries `client.session.diff({ sessionID, messageID })`, assistant message `patch` parts, completed `edit`/`write`/`apply_patch` tool calls, and workspace git status fallback, normalizing paths relative to the active project root.
     - **Project command discovery (`discoverProjectCommands`)**: inspects `package.json` (`scripts` and `packageManager` field for `bun`/`pnpm`/`yarn`/`npm`), `tsconfig.json`, `Cargo.toml`, `pyproject.toml`, `go.mod`, and environment variable overrides (`YUKIOSHI_VERIFY_COMMAND`, `YUKIOSHI_VERIFY_TEST_CMD`, `YUKIOSHI_VERIFY_TYPECHECK_CMD`, `YUKIOSHI_VERIFY_LINT_CMD`).
     - **Formatted UX output (`formatVerificationOutput`)**: prints `Verification: <STATUS> — <EXPLANATION>` to stdout after turn output, matching `main`'s UX. Emits ANSI color-highlighted status for TTY sessions, plain unformatted output for non-TTY/piped executions, and structured JSON verification events when `--format json` is active.
     - **CLI flags**: added hidden `--verify` (default `true`) and `--skip-verify` flags, preserving CLI help snapshot stability while allowing explicit opt-out.
   - **Shared core runner (`packages/core/src/verification/runner.ts`)**:
     - Extracted the turn verification workflow into `@yukioshi/core/verification` (`runner.ts`), exporting `runVerificationPipeline()`, `detectTurnChangedFiles()`, `discoverProjectCommands()`, and `executeVerificationCommand()`.
     - Reused cleanly across both `yukioshi run` and `packages/tui`, providing identical change detection, planning order, execution logic, and status derivation without code duplication.

## OS-keychain-backed credential storage

**Ported from `main` (2026-10-02) — closes plaintext credential storage security gap in `opencode-foundation`.**

1. **Investigation of `main` & `opencode-foundation` security gap**:
   - In `main`, API keys and provider tokens are stored in the OS keychain via `apps/cli/src/adapters/CliSecretStore.ts` and `@yukioshi/platform`'s `OsSecretStores.ts`.
   - `main` avoids binary C++ addons (e.g. `keytar`, which require node-gyp and break on Bun/musl), instead delegating to standard OS CLI tools (`/usr/bin/security` on macOS, `secret-tool` on Linux, and `powershell.exe` with DPAPI on Windows) while passing secrets via `stdin` to prevent argv/process-table inspection.
   - In `opencode-foundation`, `packages/opencode/src/auth/index.ts` stored all provider credentials in a plaintext JSON file (`auth.json`, permission mode `0o600`). While file-permission restricted, this left API keys vulnerable to plaintext reads if filesystem permissions are bypassed or files are backed up/synced.
2. **What was ported / implemented**:
   - **Keychain store adapter** (`packages/opencode/src/auth/keychain.ts`):
     - `KeychainStore` interface (`name`, `isAvailable()`, `get(key)`, `set(key, value)`, `delete(key)`).
     - `ProcessRunner` and `DefaultProcessRunner` abstraction for safe command execution with timeouts and stdin piping.
     - **macOS Keychain (`MacKeychainStore`)**: uses `/usr/bin/security`. Piped on stdin via `security -i` for `add-generic-password` to prevent secret exposure in `argv`/`ps`.
     - **Linux Secret Service (`SecretServiceStore`)**: uses `secret-tool` (from libsecret) with stdin streaming (`secret-tool store --label=... ...`). Probes D-Bus/X11 to detect headless CI environments where no secret service is available.
     - **Windows DPAPI (`WindowsDpapiStore`)**: uses `powershell.exe` with `ConvertTo-SecureString -AsPlainText -Force` and `ConvertFrom-SecureString` (CurrentUser scope DPAPI encryption), storing ciphertext blobs with `0o600` mode under `<dataDir>/secrets/`, decrypted in-memory via `PtrToStringBSTR`. Secrets are passed on stdin and never written to disk in plaintext.
     - **`packSecret` / `unpackSecret`**: encodes arbitrary secret strings/JSON with a `b64:` base64 prefix to prevent command parsing failures, quote stripping, or whitespace corruption across OS CLI tools.
     - **`InMemoryKeychainStore`**: zero-dependency ephemeral/test store.
     - **`createKeychainStore()`**: factory detecting platform (`darwin`, `win32`, `linux`), honoring `YUKIOSHI_DISABLE_KEYCHAIN=1` to force fallback.
   - **Auth service integration** (`packages/opencode/src/auth/index.ts`):
     - Layer & Node wiring (`makeLayer`, `makeNode`) taking a `KeychainStore`.
     - Primary storage in Keychain: all provider credentials are store-encrypted under the `credentials` key, with individual per-provider records maintained for fine-grained reads.
     - Automatic migration: if legacy credentials exist in `auth.json`, they are automatically migrated into the keychain upon first access.
     - Graceful fallback: when no keychain is available (e.g. headless Linux/CI, missing `secret-tool`/D-Bus, or disabled via env flag), seamlessly falls back to the existing `auth.json` (mode `0o600`).
     - Plaintext cleanup: when saving to the keychain, any existing plaintext file is wiped/cleared to avoid leaving stale keys on disk.
3. **What was dropped / adapted**:
   - Zero external npm dependencies: avoids native addon build requirements (node-gyp, python) and guarantees 100% Bun / Node / Alpine compatibility.
   - Base64 payload wrapping (`packSecret` / `unpackSecret`): protects multi-line or quote-rich JSON credential objects from shell-escaping truncation during stdin/CLI transmission.
4. **Test coverage**:
   - `packages/opencode/test/auth/keychain.test.ts`: 12 unit tests covering payload serialization, macOS `security -i` stdin piping, Linux `secret-tool` headless detection, Windows PowerShell DPAPI encryption/decryption, keychain-primary secure storage, keychain-unavailable `auth.json` fallback, and factory environment overrides (12/12 pass).
   - `packages/opencode/test/auth/auth.test.ts`: 4 tests validating URL normalization and key cleanup (4/4 pass). Total: 16/16 pass in `packages/opencode/test/auth/`.
