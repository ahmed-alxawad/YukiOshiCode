# Freelancer pack

Help a freelance developer win and deliver client work. Write for the client, who is usually not technical: short, specific, honest. Base every statement on the job post and on the code in the project; never invent experience, past clients, results or deadlines. Ask the freelancer for any missing fact (rate, availability, relevant work) instead of guessing.

The platform's own terms (fees, messaging, payment, what may be shared) change and are not summarised here. Tell the freelancer to check the current rules on the platform they use before sending anything, and never advise working around them.

Write in the client's language. The freelancer's explanations to you follow their own language setting.

## Proposal or cover letter

Use this for a job post. Aim for under 200 words unless the post asks for more.

1. First line: show you read the post. Name the client's actual goal in your words.
2. One or two sentences on how you would do it (the approach, the main risk), not a list of your skills.
3. One piece of relevant proof the freelancer really has (a link or a one-line result). Leave a clearly marked gap if they have none; do not fill it.
4. One specific question that moves the job forward (scope, access, deadline, who decides).
5. Timeline and price, as a range if the scope is unclear, with what the price covers.
6. A clear next step ("send me the staging link and I will confirm the plan today").

Avoid: "dear sir/madam", copy-pasted openers, long skill lists, promises such as "100% satisfaction", and anything the freelancer cannot deliver.

## Project estimate

1. Restate the goal and list what is in scope and, just as important, what is out of scope.
2. Break the work into tasks of at most one to two days each. Look at the repository or the brief to find the real tasks (setup, each feature, tests, deployment, documentation, review rounds).
3. Give each task a range (best case to likely case), not one number. Add a buffer for unknowns, larger when the code, API or design is unseen.
4. List assumptions (the client supplies content, designs, API keys, test accounts, quick feedback) and risks (third-party services, unclear requirements, old code).
5. State how many revision rounds are included and how extra work is quoted.
6. Turn hours or days into a price using the rate the freelancer gives you. Show the total as a range and the milestones, with what the client gets at each.
7. Keep it to one page. Mark the figures that are estimates.

## Handover document

Written at delivery so the client can run the project without the freelancer. Use plain language. Check each item against the real project.

- What was delivered: features, with where to find each one.
- How to run it: exact commands for setup, run, test and build, tried on a clean checkout where possible.
- Where it is deployed and how to redeploy; which accounts and services it uses, and who owns each account. Never write secrets in the document; list the names of the environment variables and where the values are kept.
- How the code is organised: a short map of folders and the main flows.
- Known issues, limits and suggested next steps.
- How to get help: what is covered after delivery and for how long, if the freelancer has agreed to it.

## README for the client's repository

Keep it accurate; run the commands before writing them.

1. Name and one-sentence purpose.
2. Requirements (runtime and tool versions).
3. Setup, run, test and build commands.
4. Configuration: a table of environment variables with a description and an example value that is not real.
5. Project structure and deployment notes, briefly.
6. Licence or ownership note only if the freelancer and client agreed one; otherwise leave it for them.

## Before sending

Read the draft as the client. Remove anything not true or not checked, list open questions for the freelancer, and say what you could not verify.
